# Development Lifecycle

## Purpose

This document defines the standard development lifecycle used across the KingC Software ecosystem.

The purpose is to create a consistent, repeatable process for building reliable software while maintaining quality, documentation and engineering discipline.

---

# Development Philosophy

KingC Software follows the principle:

> We don’t just write code. We build software that lasts.

Development is not only about producing working features.

Every change should consider:

- Quality
- Maintainability
- Testing
- Documentation
- Future development
- Long-term reliability

---

# Lifecycle Overview

Every piece of work follows this process:


Understand
↓
Plan
↓
Build
↓
Test
↓
Document
↓
Commit
↓
Verify
↓
Complete


---

# Phase 1 — Understand

## Objective

Before building anything, understand the requirement.

Activities:

- Read relevant documentation.
- Understand the problem.
- Confirm the expected outcome.
- Identify affected systems.
- Identify risks.

No implementation should begin before understanding the task.

---

# Phase 2 — Plan

## Objective

Create a clear approach before making changes.

Activities:

- Define the solution.
- Identify required files.
- Identify dependencies.
- Break larger work into atomic tasks.
- Confirm implementation approach.

Planning prevents unnecessary complexity.

---

# Phase 3 — Build

## Objective

Implement the planned solution.

Development rules:

- Keep solutions simple.
- Follow existing architecture.
- Maintain coding standards.
- Avoid unnecessary changes.
- Protect working software.

---

# Phase 4 — Test

## Objective

Verify the change works correctly.

Testing includes:

- Feature testing.
- Error checking.
- Regression testing.
- Integration testing where required.

A change is not complete until it has been tested.

---

# Phase 5 — Document

## Objective

Ensure knowledge is preserved.

Documentation should include:

- What changed.
- Why it changed.
- How it works.
- Any important decisions.

Documentation is part of development, not an optional extra.

---

# Phase 6 — Commit

## Objective

Create a safe record of completed work.

Git rules:

- Commit working changes.
- Use meaningful commit messages.
- Keep commits focused.
- Maintain clean history.

Example:


Add user authentication documentation


---

# Phase 7 — Verify

Before completing any task confirm:

## Saved?

YES

## Git?

YES

## Graphify?

YES (where required)

## Documentation?

YES

Only after verification is the task complete.

---

# Phase 8 — Complete

A completed task should leave the repository:

- Working.
- Tested.
- Documented.
- Committed.
- Clean.

Then move to the next task.

---

# AI Employee Workflow

All AI employees follow this lifecycle.

AI employees must:

- Understand before acting.
- Explain important decisions.
- Follow documented standards.
- Maintain repository quality.
- Update documentation when required.
